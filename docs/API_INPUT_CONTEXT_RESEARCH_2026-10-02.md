# 辅助 API 输入膨胀研究（2026-10-02）

本文件记录优化前的固定版本。后续已实现优化，见 [实现与验收记录](API_INPUT_OPTIMIZATION_2026-10-02.md)。下方历史复现脚本的 current 项需在 ffc777c0bdff81bd3584bf189c97038b98100458 的隔离工作树中运行；当前代码验证使用 scripts/auxiliaryContextRegression.mjs。历史测量结果保留，不覆盖为优化后数据。

## 结论与研究边界

世界演化、规划分析和剧情回忆的大输入，主要来自继承的上下文拼装设计：全量状态、较长的完整正文窗口、没有真正生效的候选过滤，以及部分注入链路缺少字数上限。固定提示词和强制长篇分析还增加了处理、生成成本。

当前版与原版在相同离线样例下，七组基础请求和上下文增长样例的字符量完全一致；新增诊断功能没有造成这些样例的输入膨胀。玩家修改版有可借鉴的小说注入上限，但仍保留相同的回忆库问题，还存在附加内容重复注入、默认世界书预算更宽松的情况。不能把整套玩家版当作输入优化方案直接移植。

本次只研究与记录，没有修改游戏运行代码、存档或调用真实模型。实际诊断只有请求总字符数和提供方 usage，没有分块输入统计，因此可以确认设计缺陷，但不能断言本回合的 28 万字符具体有多少来自世界树、小说或世界书。

## 一、剧情回忆：预筛只打标记，整个回忆库仍会发送

当前链路：

1. 本地根据玩家输入评分，通常选最多 24 个候选，并保留近期候选。
2. 把候选 ID 传给构建检索上下文的函数。
3. 构建函数仍对全部回忆档案 sorted.map；候选 ID 只增加“可能相关”标记。
4. 默认最近 20 条档案发完整原文，之前的每一条发概括，再让模型检索。

关键位置：当前 hooks/useGame/recallWorkflow.ts:40、hooks/useGame/memoryRecall.ts:148、165、169。三版 memoryRecall.ts 内容一致。见[原版回忆检索构建](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/hooks/useGame/memoryRecall.ts#L148)。

所以候选数量受限，发送语料数量不受限。回忆档案逐回合追加；短期/长期记忆池的整理也不会自动把回忆档案限制成同样数量。

离线样例每条原文 1,500 字符、概括 100 字符，三版结果一致：

| 总档案数 | 本地候选数 | 实际发完整原文 | 实际发概括 | 检索语料字符数 |
| ---: | ---: | ---: | ---: | ---: |
| 23 | 23 | 20 | 3 | 31,125 |
| 100 | 24 | 20 | 80 | 40,378 |
| 1,000 | 24 | 20 | 980 | 149,260 |

另一个断言只传入一个候选 ID，未入选的旧概括仍被发送。预筛没有实现输入减量。

此次日志约有 23 个助手回合，因此单看“24 个候选”，这一局还不足以筛掉档案。近期 20 条完整原文才是短局也会较大的直接来源。回忆原文来自玩家输入和正文日志，并不等于把原始 API thinking/命令整体存进原文；未发现回忆标签递归嵌入历史输入的证据。

## 二、世界演化：完整世界树加多套近期材料

当前主要组成：

- 完整规范化世界状态，包括地图及内部建筑、历史记录、事件和人物活动等保留字段。
- 世界观提示词。
- 最近 6 回合完整脚本，其中包含玩家文本、助手正文及可用规划信息。
- 最近 8 条短期记忆。
- 本回合正文、规划、命令、剧情锚点、到期事件与动态提示。
- 开启对应功能时的世界书、小说分解和同人补充。

关键位置：hooks/useGame/worldEvolutionWorkflow.ts:126、161、164、205；worldEvolutionUtils.ts:165。见[原版世界演化工作流](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/hooks/useGame/worldEvolutionWorkflow.ts#L126)及[上下文构建](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/hooks/useGame/worldEvolutionUtils.ts#L165)。

这里的“规范化”负责字段形状和有效性，不负责总长度。JSON 美化、显示数组原始索引以及移除少数展示字段，也不构成内容预算。剧情锚点虽限制历史卷宗为最近两份，当前章节和预告等字段仍可继续增长。

完整正文、短期概括、本回合正文和规划之间存在内容重叠。当传入历史已经包含当前回合时，离线样例的当前正文与规划标记各出现两遍；正常自动工作流的历史可能尚未包含当前回合，不能断言每次都有完全相同的两份正文。

增长验证：一个合法地图描述字段增加 100,000 字符后，三版都会把它完整送出。当前版实际世界演化请求达到 113,894 字符。即使这段描述对本次演化不相关，也没有统一相关性筛选或总预算拦截。

## 三、规划分析：世界、社交和规划均按全量发送

当前规划输入包括完整剧情/规划结构、完整世界树、完整社交列表、环境、最近 3 回合完整正文、当前规划，以及角色与结构规则。开启女主规划、同人等功能时再增加对应内容。

关键位置：hooks/useGame/planningUpdateWorkflow.ts:197、291、304、306、311。见[原版规划拼装](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/hooks/useGame/planningUpdateWorkflow.ts#L291)。

代码里的“裁剪修炼体系上下文数据”主要根据开关移除修炼字段；开启时可以原样返回。它不会把全量世界改成任务相关实体，也不会把全量社交列表限制为相关人物。

社交规范化仍会保留人物档案中的多种状态和记忆等信息；规划没有专门的 NPC 简要视图。不能据此推断本次发送了大量图片二进制：图像字段有其他处理，诊断也没有该块统计。

离线隔离字段测试：规划世界字段增加 100,000 字符后请求达 119,141 字符；社交人物记忆字段增加同等长度后请求达 118,478 字符，均完整保留。

规划通常使用世界演化更新后的状态，二者存在状态依赖。直接并发不能解决输入膨胀，还可能令规划读取旧状态，需要先定义状态版本与合并规则。

## 四、两个额外的预算漏洞

### 小说分解：当前版和原版的链路上限固定为零

当前 services/novelDecompositionInjection.ts:921 的“获取链路上限”忽略 settings 和 target，直接返回 0，含义为不限。它并没有按配置限制最终注入长度。即使采用当前/下一章节滑窗，单组事实、事件或进度字段仍能很长；快照回退也缺少该总上限。

见[原版小说注入上限](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/services/novelDecompositionInjection.ts#L921)。

玩家版实现了辅助链路“小说拆分详细注入上限”，默认 4,000 字符，自定义值参与裁切。见[玩家版限制函数](https://github.com/ypq123456789/MoRanJiangHu/blob/5f7a3e4a73496f7914ed0dae217520a275f6db15/services/novelDecompositionInjection.ts#L958)和[默认配置](https://github.com/ypq123456789/MoRanJiangHu/blob/5f7a3e4a73496f7914ed0dae217520a275f6db15/utils/apiConfig.ts#L880)。

合成一个已完成且启用注入的章节组，放入三个各 100,000 字符的事实字段：规划滑窗原始文本 300,366 字符；当前版/原版有效上限为 0，保留全部；玩家版默认有效文本限制为 4,000 字符。当前版在此函数里连自定义 5,000 也不会生效。

这是可借鉴的修复，但玩家版使用字符串截断，可能切掉完整事实或关键约束。真正实施宜按完整条目分配预算，保留章节门槛、硬约束和来源 ID。本测量证明容量漏洞，不证明本回合启用了如此大的小说分解。

### 世界书：第一条超大条目可以绕过预算

当前版和原版的世界演化预算为 4,000 字符，规划相关作用域为 5,000。utils/worldbook.ts:1190 的预算检查要求 selected.length > 0，因此第一条条目再大也能通过。见[原版世界书选择逻辑](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/utils/worldbook.ts#L1190)。

离线验证：第一条内容 100,000 字符，仍被选中，带标题后的注入 100,025 字符，显著超出名义预算。

玩家版在显式 maxChars 下有更严格检查，但默认路径只给关键词匹配条目计算预算，常驻 always 条目不受相同总预算约束；首个关键词匹配条目仍可绕过预算。三个各 3,000 字符的常驻条目，当前/原版只选一个，玩家版默认选三个。见[玩家版世界书默认预算分支](https://github.com/ypq123456789/MoRanJiangHu/blob/5f7a3e4a73496f7914ed0dae217520a275f6db15/utils/worldbook.ts#L1280)。

## 五、固定规则和强制分析也很重

在合成的最小状态、开启显式 COT/预填、没有实际玩家世界观/小说/世界书长文本时，捕获真实请求得到：

| 请求场景 | 当前版 | 原版 | 玩家版 |
| --- | ---: | ---: | ---: |
| 世界演化，普通 | 22,747 | 22,747 | 29,997 |
| 世界演化，同人 | 25,420 | 25,420 | 32,670 |
| 规划，无女主/同人 | 18,424 | 18,424 | 19,141 |
| 规划，女主+同人 | 27,097 | 27,097 | 27,759 |
| 回忆，最小语料 | 633 | 633 | 784 |

单位均为 Unicode 字符，不是 tokens。这是相同测试配置下的框架开销，包含默认世界演化规则等测试上下文，不代表任意真实局的严格最小值或平均值。

当前普通世界演化样例中，系统规则 10,554 字符、上下文消息 5,861、COT 6,225，另有触发和预填；普通规划仅结构参考和 COT 就分别 4,379 与 5,980 字符。

世界演化要求 Step0～Step15，每步至少三条列点，等于至少 48 条；规划要求 Step0～Step9，每步至少三条，等于至少 30 条，即使无需更新也要完成全部审计。见[世界分析协议](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/prompts/runtime/worldEvolutionCot.ts#L10)、[规划分析协议](https://github.com/MikuLXK/MoRanJiangHu/blob/bfca81e7bb04ba50fd45b1953462e3fb4409033e/prompts/runtime/planUpdateReference.ts#L26)。

若提供方还输出独立 reasoning_content，再要求正文写 thinking，就有两层分析输出的成本。现有日志不能精确分离正文 thinking 和最终命令各占多少，因此不作量化归因。

回忆的固定提示词本身很短，不能用上述 16/10 步规则解释其全部耗时；该任务主要需要控制检索语料与任务推理/输出预算。

## 六、玩家版仍有附加内容重复注入

玩家 services/ai/storyTasks.ts:873、884 将世界演化 extraPrompt 放入任务文本和 system；规划 :1892、1907 也同时放入两处。见[玩家版世界请求](https://github.com/ypq123456789/MoRanJiangHu/blob/5f7a3e4a73496f7914ed0dae217520a275f6db15/services/ai/storyTasks.ts#L873)及[玩家版规划请求](https://github.com/ypq123456789/MoRanJiangHu/blob/5f7a3e4a73496f7914ed0dae217520a275f6db15/services/ai/storyTasks.ts#L1892)。

在附加文本里加入唯一标记并捕获请求，当前版/原版均一份，玩家版两份。附加包为 10,000 字符加标记时，玩家版会承担约双倍该包的增量。如果世界书/小说内容通过这个参数传入，重复范围也会相应扩大。

玩家版的后台计算和计时改进可以改善交互或观测，但本次测量没有显示其核心辅助输入整体更小；小说上限是具体有效的局部改动。

## 七、建议的修复顺序与验收条件（未实施）

| 顺序 | 建议 | 验收重点 |
| --- | --- | --- |
| 1 | 诊断增加分块字符数、条目数、筛选前后数量和重复注入标识 | 能把总量拆成规则、世界、社交、近期正文、回忆、世界书、小说等；记录实际发送前后，不保存完整提示词/凭据 |
| 2 | 回忆真正筛选候选：本地检索后发有限摘要，少量必要原文再按需读取 | 1,000 条存档也受发送预算约束；远期相关回忆可命中；所有原始档案保留 |
| 3 | 恢复小说辅助链路预算，修复世界书首条和常驻条目漏洞，附加包只注入一次 | 首条超大、多个常驻、自定义上限、回退路径都有边界；不能截断关键门槛和实体 ID |
| 4 | 世界/规划使用各自任务视图与总预算 | 世界保留到期/触发/相关异地事件；规划保留相关人物与当前章节约束；全局历史、人物物品表等不再默认全量发送 |
| 5 | 缩短固定规则与无需更新时的分析，按任务配置输出/推理预算 | 无更新时可快速完成；有更新时命令格式有效；验证提供方参数语义，避免简单降低 maxTokens 导致命令截断 |

任务视图只改变 API 读取范围，不删存档。回忆名称、NPC ID、世界数组原始索引/来源索引必须稳定，尤其不能过滤数组后重新编号导致写回错对象。世界演化也不能只看当前地点，否则会丢失异地事件与世界推进。

世界与规划之间保持明确的状态依赖；任何并发或后台优化另行验证读取版本、写回顺序和冲突策略。不能用“并发更快”替代输入预算修复。

## 最终判断

底层可以修复，重点是为每项辅助任务设计相关性视图和真正执行的输入预算。回忆预筛无减量、小说上限固定零、世界书首条绕过预算都有可复现的代码证据；世界/规划全量状态和强制长篇分析属于系统设计负担。

本回合世界演化 280,527 字符、规划 230,454 字符的分块占比仍需新增诊断才能确认。实施前应先补这一证据，避免只调小某个窗口却遗漏真正占大头的注入包。
